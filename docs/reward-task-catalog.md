本文件保存 2026-08-24 至 2026-08-31 於 BS5 台灣版取得的遊戲規則、座標與實機觀察。它是有日期的驗證紀錄，不是公開任務清單的唯一來源；目前 23 個公開任務與已知缺口請以 [任務參考](./task-reference.md) 為準。

## 介面規則

- 所有領獎入口只顯示一個 Maa 任務：`ClaimAllRewards`（領取所有獎勵）。
- 家園床與推車掛機收益已接入統一領獎流程；目前公開 root 實際在這裡結束。
- 好友、餽贈、任務、商城與精彩活動保留為內部 Pipeline，但 `HomeRewards.Done` 尚未接到 `Rewards.FunctionList.Start`。在完成串接與實機驗證前，不得把 `ClaimAllRewards` 的完整介面說明視為已實作。
- 需要玩家實際完成條件的項目才建立獨立 Maa 任務；尚未取得完整進場與停止畫面的項目維持安全骨架，不會假裝執行成功。

## 家園商店購物

`HomeShopPurchase` 是日常與秘寶大作戰共用的單一 Maa 任務，不為「購買 2 次」與「購買 4 次」重複建立任務。

- 每日雜貨刷新次數上限可設為 0～10 次，現在預設 0 次。
- 六種素材與「其他」可各自設定折數上限；木材、石塊與「其他」預設不限折數，其餘預設如下。
- 粗煉石（黑色的鐵）預設 7 折以下購買。
- 稀有的時之沙（黃色的砂）預設 8 折以下購買。
- 歷戰精華（紫色）預設 9 折以下購買。
- 普通凍乾（咖啡色）預設 6 折以下購買。
- 寶庫前三排共九格，各自可設為不購買、1～9 折以下或不限折數；未指定前預設不購買。
- 特賣商品可設為不購買、1～9 折以下或不限折數；沒有特賣時直接略過，預設不購買。
- 雜貨判斷必須同時符合商品圖示與折數上限。購買動作只允許點擊該商品下方的黃色價格按鈕。
- 刷新後尚未購買的原始 `720×1280` 樣本保存在 `tests/screenshots/home-shop-grocery-top-refreshed.png`，六種素材圖示已拆到 `resource/base/image/home_shop/`。

2026-08-29 已在 BlueStacks 5（`emulator-5564`，720×1280）實機確認購買機制：點一下商品下方的黃色價格按鈕即成交，沒有二次確認彈窗；成交後該商品圖片區改顯示「售完」且整張卡片轉灰。刷新同樣是一點即刷，沒有確認彈窗。

### 版面

雜貨與寶庫共用同一組 3×3 格線（720×1280 直式座標）：

| 元素     | 中心座標                   |
| -------- | -------------------------- |
| 折數徽章 | `(38 + 229c, 200 + 283r)`  |
| 商品圖示 | `(132 + 228c, 293 + 282r)` |
| 售完標示 | `(132 + 228c, 297 + 282r)` |
| 價格按鈕 | `(132 + 228c, 410 + 282r)` |

### 雜貨

前三排 9 格是每日輪替的折扣商品，第四排以後是固定商品（無折數、無限購），流程不處理。

商品種類以圖示模板比對判定，共六種素材加上「其他」：木材、石塊、粗煉石、稀有時之沙、歷戰精華、普通凍乾。「其他」是第一排低機率出現的稀有商品（例如飾品），判定方式是「六種素材圖示都比不中」。

**圖示比對門檻必須 ≥ 0.85**：實測木材模板比對石塊會拿到 0.674，門檻設 0.6 會誤判成木材。

每一類都可獨立設定折數上限，共 12 種選擇：1～9 折以下、「不限折數（只要有折扣就買）」、「不限折數（含原價，一律購買）」、不購買。

前十種都靠折數徽章的 OCR 判斷，因此**沒有折數標籤的原價商品買不到**；要連原價一起買必須選「含原價，一律購買」，該模式改用 `DirectHit` 直接點價格按鈕，不看折數。

右上角可花金幣刷新，費用遞增（實測 4000 → 8000），刷新後會重新掃一輪。刷新次數上限由 `HomeShopRefreshLimit` 設定，預設不刷新。

### 寶庫

前九格商品固定、折數每日變動，使用晶石購買，每格可獨立設定折數上限，預設全部不購買。第 1 格通常是每日免費體力，由獨立的「免費」文字辨識自動領取。

**第 3 格每日限購 2 次**，其餘每格 1 次。購買後會回到該格重新檢查「售完」，因此限購多次的格子會連續買到上限或售完為止。

領完後按鈕文字仍是「免費」（只是轉灰），所以領取節點以 `max_hit: 3` 收斂，最多會多點兩次沒有作用的按鈕。

### 特賣

每日不定期出現，固定只有一個商品，使用晶石購買，可設定折數上限，預設不購買。

## 固定安全規則

- 家園商店的雜貨以金幣購買，預設依各素材的折數上限自動購買；寶庫與特賣使用晶石，預設全部不購買，需使用者自行開啟。刷新會花金幣且費用遞增，預設不刷新。
- 探尋命運等尚未確認免費條件與停止規則的任務，維持 `DoNothing` 骨架。
- 祈願、扭蛋、結緣已由使用者明確授權執行，並以畫面上的「今日已祈願／已開啟／已結緣」計數驗證實際執行結果。
- 任務獎勵只點擊「領取」或「全部領取」，不從領獎流程點擊「前往」。
- 月卡只允許點擊明確辨識到的「領取」；顯示「延長」、價格或購買文字時安全結束。
- 所有循環必須設定最大處理次數，找不到可靠狀態時安全結束。

重要觀察：

- **這款遊戲不吃 Android 系統返回鍵（`ClickKey key: 4`）**。所有返回都必須點畫面左下角的返回按鈕（約 `(75, 1218)`）。在家園首頁時該座標是「角色」頁籤，因此收尾流程必須先判斷是否已在家園再決定要不要點。

- 家園禮物泡泡**要點泡泡下方的 NPC 本體**（模板框往下偏移 55px），直接點泡泡本身不一定有反應。
- 分解頁的「排除高戰力」在每次重新進入時會回到勾選狀態。
- 「一鍵使用」單次上限 100 個；需要自行挑選內容的寶箱不會被一鍵使用。

## Custom Action Agent（次數計算）

MaaFramework 的 pipeline（JSON）沒有變數、算術與狀態，因此「輸入總次數自動拆成 100／10／1 抽」與「扣除今日已抽過的次數」無法用 pipeline 表達；`interface.json` 的 `input` 選項也只是純字串代換（`max_hit: "{Count}"`），沒有運算能力。

解法是 MaaFramework 的 Agent：MXU 依 `interface.json` 的 `agent` 設定啟動 `agent/main.py` 子行程，兩邊以本機 socket 溝通，pipeline 用 `"action": "Custom", "custom_action": "PullByCount"` 呼叫過去。

`PullByCount` 由幻獸結緣、女神像祈願、時光扭蛋機與公會捐贈共用，參數以 `profile` 區分：

1. OCR 讀「今日已結緣／已祈願／已扭蛋（結果畫面寫「已開啟」）」計數。
2. 依 `deduct_done` 決定 total 是「今日累計目標」還是「本次要抽的次數」。
3. 貪心選用不會超抽的最大按鈕；按鈕會因貨幣不足而消失，找不到就退到較小的。
4. 每次點擊後重讀計數確認有進展，連續兩次沒動就判定資源不足並安全停止。

實作要點：

- Agent 子行程**不可**直接呼叫 `controller.post_click`（控制器在主程式端），必須用 `context.run_action_direct(JActionType.Click, JClick(...))` 代理。`post_screencap` 則可以直接用。
- 辨識結果的 `box` 在這個版本是 `[x, y, w, h]` 陣列而非 Rect 物件。
- Agent 要讓訊息出現在 MXU 日誌，可透過 `context.run_task("Agent.Log", {...focus...})` 推回通知管道；直接 print 只會留在子行程的 stdout。
- Python `maafw` 套件版本必須對上 MXU 使用的 MaaFramework 版本（目前 **v5.12.3**）。注意 `maa-tools` 下載的是另一個版本（v5.13.0-beta.5），拿它驗證不等於驗證了 MXU 的行為。

### 次數選項的覆寫寫法

「次數」與「是否扣除」拆成兩種機制，避免依賴 `pipeline_override` 的合併語意：

- 是否扣除 → 用 `next` 路由，`{P}.Pull.Route` 指向 `{P}.Pull.Deduct` 或 `{P}.Pull.Raw`。
- 次數 → 對 Deduct／Raw **兩個節點都寫入完整的** `custom_action_param`（含 `profile` 與 `deduct_done`），這樣不論覆寫是深層合併還是整包取代都正確。

## Pipeline 撰寫上的共同陷阱

`next` 只列一個候選時，該候選辨識失敗會讓**父節點連帶失敗**，整個任務中斷。已知踩過的例子：

- 設施進場後的 `Screen` 節點只指向一個後續動作 → 背包沒有可一鍵使用的道具時被判成任務失敗。
- 祈願池的 `Screen` 只指向 `Pool.Select` → 目標池被捲到畫面外就直接中斷。
- 刷新選項把 `RefreshRoute.next` 覆寫成只有 `Refresh` → 刷新次數用完後 `Refresh` 被 `max_hit` 跳過，`RefreshRoute` 失敗。

原則：**每個 `next` 都要有一條保證可走的收尾路徑**（DirectHit 的 Skip／Done／安全結束節點）。Custom Action 回傳失敗時另以 `on_error` 導回返回家園的節點。

## Pipeline 保底路徑與 `pnpm audit:pipeline`

MaaFramework 在節點執行完後會依序辨識 `next` 清單裡的候選；**全部失敗時這個節點就算失敗，並往上層傳播**，最後整個任務中止。因此「本來就沒東西可做」這種合理狀態，如果沒有保底候選，就會被回報成任務失敗。

實際踩過的例子：

- 背包沒有可一鍵使用的道具 → `Bag.Screen.next` 只有 `Loop.UseAll`，被判定成任務失敗。
- 目標祈願池被捲到畫面外 → `GoddessStatue.Screen.next` 只有 `Pool.Select`，直接中斷。
- 雜貨刷新次數用完 → `RefreshRoute.next` 被選項覆寫成只有 `Refresh`，`max_hit` 用盡後失敗。
- 特賣分頁當天沒出現 → 寶庫最後一格的 `next` 只有 `Sale.Tab`，整個商店任務失敗。

`tools/audit-pipeline.mjs`（`pnpm audit:pipeline`）會做兩件事：檢查 `next` / `on_error` 參照是否存在（缺少時以非零結束碼失敗），並列出「唯一候選且該候選不是 DirectHit」的高風險節點。後者是提示而非錯誤——導航與進場重試鏈本來就靠父節點的多個候選吸收失敗，已排除在外；其餘要逐一判斷「這一步的辨識有沒有可能合理地失敗」。
